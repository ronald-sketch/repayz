# ePortal API - Complete Documentation Summary

Based on the official Envipco ePortal API documentation (22 pages).

---

## 1. General Information

- **Base URL**: `https://ePortal.envipco.com/api/`
- **Authentication**: Login returns an `ApiKey` valid for 15 minutes
- **Rate Limit**: 1000 calls per day per user
- **Response Format**: JSON or CSV depending on endpoint

---

## 2. API Endpoints

### 2.2.1 Login API
```
GET /api/login?username=USER&password=PASSWORD
```
Returns: `{"ApiKey": "ef1e65a6-c07f-11ea-a2fd-00219b9777e5-334633"}`

### 2.2.3 rvmStats API (Main endpoint we use)
```
GET /api/rvmStats?apiKey=KEY&rvms=MACHINE_ID&rvmDate=YYYY-MM-DD
```

**Key fields in response:**

| Field | Description |
|-------|-------------|
| `RVMStatusBarcodeCount` | Total barcodes scanned |
| `RVMStatusBarcodeDate` | Last barcode scan date |
| `RVMStatusError` | Error counter |
| `RVMStatusProcessing` | Items per minute currently processing |
| `RVMStatusReady` | Ready counter (non-zero = ready) |
| `RVMStatusStateDateGMT` | State change date in GMT |
| `RVMStatusLastTime` | Last status update time |
| `RVMStatusReportDate` | Last report date |
| `StatusInfoState` | **Current machine state** ("Ready", "Error", "Door", etc.) |
| `StatusInfoMeter` | Lifetime total items processed |
| `StatusInfoProcessing` | Currently processing |
| `StatusInfoUptime` | Uptime in minutes |
| `StatusInfoRestarts` | Number of restarts |
| `StatusInfoReboots` | Number of reboots |
| `BinInfoMaterialBin1` | Material type in bin 1 (e.g., "ALU") |
| `BinInfoMaterialBin2` | Material type in bin 2 (e.g., "PET") |
| `BinInfoCountBin1` | Items count in bin 1 |
| `BinInfoCountBin2` | Items count in bin 2 |
| `BinInfoLimitBin1` | Bin 1 capacity limit |
| `BinInfoLimitBin2` | Bin 2 capacity limit |
| `BinInfoFullBin1` | Bin 1 full indicator |
| `BinInfoFullBin2` | Bin 2 full indicator |
| `pet_accepted` | PET bottles accepted today |
| `cans_accepted` | Cans accepted today |

### 2.2.7 Events API
```
GET /api/events?apiKey=KEY&rvms=ID&startDate=DATE&endDate=DATE
```
Returns event history in CSV format.

### 2.2.9 Receipts API
```
GET /api/receipts?apiKey=KEY&startDate=DATE&endDate=DATE&rvms=ID
```
Returns receipt data including deposit amounts and container counts.

### 2.2.10 Rejects API
```
GET /api/rejects?apiKey=KEY&startDate=DATE&endDate=DATE&rvms=ID
```
Returns rejected containers with reasons (noBarcode, notInDb, bcMove, sortingErr, etc.)

## 4. Asynchronous Events (Generated by ePortal)

### 4.1 Ping - Event 40005
Sent every 30 minutes to REST endpoint if configured.

### 4.2 REST API Delivery Failure - Event 40009
Sent via email if REST endpoint fails.

### 4.3 Receipt Data - Event 40010
Sent when receipt is printed (if configured).

### 4.4 State Change - Event 40011 ⭐ IMPORTANT

**The 4 machine states that are tracked:**

| State | Description |
|-------|-------------|
| **Error** | Machine has an error |
| **Ready** | Machine is operational and ready |
| **Door** | Door is open |
| **Door(Tech)** | Door is open AND technician logged in |

**Example JSON:**
```json
{
  "events": [{
    "siteId": "999626",
    "rvmId": "999626",
    "eventId": 40011,
    "event": "State of the machine changed.",
    "time": "2021-12-08T13:43:30",
    "eventData": {
      "machineState": "Ready"
    }
  }],
  "customData": "test2"
}
```

### 4.5 RVM Missed Check-ins - Events 40012, 40013, 40014

| Event ID | Description |
|----------|-------------|
| 40012 | RVM missed 2 back-to-back reports (considered offline) |
| 40013 | RVM missed 5 reports |
| 40014 | RVM missed 10 reports |

## 5. Key Findings for REPAYZ Implementation

### Current Status Logic
The current code uses:
```typescript
status: rvmData.RVMStatusReady ? 'operational' : 'offline'
```

### Recommended Status Logic
Based on the documentation, we should use `StatusInfoState`:

```typescript
function determineStatus(rvmData: any): 'operational' | 'error' | 'door_open' | 'maintenance' | 'offline' {
  const state = (rvmData.StatusInfoState || '').toLowerCase();
  
  switch (state) {
    case 'error':
      return 'error';
    case 'door':
      return 'door_open';
    case 'door(tech)':
      return 'maintenance';  // Technician is working on it
    case 'ready':
    case '':  // Empty string means ready
      return 'operational';
    default:
      // Fallback to RVMStatusReady
      return rvmData.RVMStatusReady ? 'operational' : 'offline';
  }
}
```

### Bin Full Detection
Check `BinInfoFullBin1` and `BinInfoFullBin2`:
- Negative value (e.g., -2) = NOT full
- Positive value or 0 = Full (needs verification)

Or use events 9200-9214 for push notifications.

## 6. Summary

The ePortal API provides:

1. **Real-time status** via `StatusInfoState` field with 4 states: Error, Ready, Door, Door(Tech)
2. **Counters** for items processed (daily and lifetime)
3. **Bin fill levels** via BinInfo fields
4. **Push notifications** for events like bin full, state changes, offline detection
5. **Historical data** via events, receipts, and rejects endpoints

The `StatusInfoState` field is the most reliable way to determine machine status, not `RVMStatusReady` which is just a counter.
